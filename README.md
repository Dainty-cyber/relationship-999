# 确定关系前的 99 / 999 问 · 遇见彼此

奶油白与浅粉色的手机抽签网页，支持个人抽签与双人独立回答。网页无需账号，前端无框架、无 npm 依赖，正式页面位于 `dist/`；双人模式使用 Sites / Cloudflare D1 服务端同步。

已按用户提供的 Word 文档导入全部 999 题，保留原始题号与文字。核对结果：题号 1–999 连续，无空题、重复题号或重复内容。

**抽签规则：聊完后点「已聊完」，也可以把问题暂放到「待聊」再继续，本轮不重复。精简版前 98 题、完整版前 998 题全部确认后，才解锁各自的最后一题；暂放的题不算聊完。无需填写或上传答案。**

以上为个人抽签规则。双人回答可从当前卡片下方的「和 TA 一起答」进入，详见下方说明。

## 双人独立作答，一起揭晓

1. 抽签后点击「和 TA 一起答」，填写称呼并创建房间；当前普通问题可成为双人模式的第一题。也可以直接打开 `pair.html`，选择 99 / 999 问开始。
2. 把邀请链接发给对方。每个房间只允许两人，无需登录。对方加入后，两人看到同一道原题，各自回答自己的想法。
3. 选最接近自己的选项，或选择「我想自己说」。精简版 99 题逐题整理了选项；完整版中不适合选择题的问题保留自由填写。所有题都允许补充文字，最多 500 字。选项与原文分开保存，不改写题库。
4. 点击「提交并锁定我的答案」后不可修改。只有一方提交时，另一方的接口响应、页面与历史中均不包含这份答案；服务端在双方都提交后才一起放开答案。不同设备会因网络延迟稍有显示时差。
5. 双方均点「我看完了」后才计入共同进度、允许抽下一题。前 98 / 998 题共同完成后，才会解锁原题号 999。任何一方都不能跳过对方确认或提前进入下一题。

双人模式开启独立的新一轮，不导入个人版的「已聊完」记录，不改动原有个人进度、待聊或备份。双人房间不支持单方面暂放或修改已提交的答案，可在揭晓后继续交流。

### 双人数据与恢复

- 回答会同步保存到服务端，房间参与者可查看已共同揭晓的历史。昵称和内容以纯文本显示，不把回答传给第三方分析或 AI 服务。
- 本浏览器保存各自的随机身份令牌；服务端仅保存令牌哈希。邀请链接包含一次性的另一席位凭证，不包含房主身份令牌。链接中的邀请凭证放在片段中，打开后移除，不进入普通 HTTP 路径或 Referer。
- 原浏览器刷新或重新打开可以恢复房间；未提交草稿只保存在当前标签页的 `sessionStorage`。清除浏览器数据或换浏览器会丢失本席位身份，个人进度备份不包含双人房间身份或回答。
- 房间从创建起 7 天有效，到期不可访问，并在访问或后续创建房间时清理过期数据。任一参与者可在确认后结束并删除整个房间及双方回答，邀请随即失效。没有账号恢复功能。
- 存储受限时会显示提示，身份仅在当前打开期间保留。网络响应丢失时先重新同步确认提交状态，避免把一次提交误当作未提交。

### 双人开发与服务端

使用 Node.js 24 或更高版本，在本机启动含真实 SQLite 的双人预览（房间数据仅在该进程内保留）：

```powershell
npm run preview:pair
```

生产服务使用既有 Sites 项目，公开地址在 `dist/pair-config.mjs` 中配置。GitHub Pages 仅发布前端，通过限定来源的 CORS 和每席位 Bearer 令牌访问服务。`server/pair-service.mjs` 为协议，`server/d1-repository.mjs` 使用 D1 的批量事务和修订号比较更新，处理同时提交和重复请求。数据库结构和生成的迁移位于 `hosting/`，运行时不执行建表。

`scripts/prepare-pair-host.mjs` 将当前前端与服务端移入已经通过 Sites 源码 helper 打开的原项目，使用官方 Vinext 模板保留 `sites()` 集成，并保留项目 ID、Git 历史和已生成的迁移。独立的源代码目录与 GitHub 前端目录分开，构建产物不上传 GitHub Pages。部署前应先完成 Sites 服务端部署，再发布 GitHub 前端。

房间 API 不使用公开 GitHub 仓库或 Issues 保存回答，也没有把服务端密钥放进网页。请勿把真实房间身份或本机测试数据库提交到仓库。

## 精简版与完整版

页面提供 **精简版 99 问** 和 **完整版 999 问**，随时切换，各自保存抽签和「已聊完」记录。重置只清空当前版本。

- 精简版：从原题库精选固定 98 题，涵盖日常喜好、情绪、表达、冲突、边界、金钱、家庭和成长八个话题；第 99 题保留原题库的最后一题。前 98 题全部确认后才可揭开它。
- 完整版：保留原来的 999 题和抽签规则。题库内容、浏览器存储键和题库指纹均保留，原有进度不会因增加精简版而清空。
- 新用户默认精简版；已有完整版记录且尚未选择过版本的用户，自动续接完整版。之后会记住所选版本。
- 精简版按 1–99 显示编号，同时标注原题号；题目文字全部来自原文。精选原题号和话题分组位于 `dist/editions.mjs`，没有复制或改写正式题目。
- 「分享给 TA」链接包含当前版本 `?edition=concise` 或 `?edition=full`；访客会打开指定版本，各自记录仍然独立。

## 本地预览

仅预览个人网页需要 Node.js 22 或更高版本；运行全部测试与双人预览需要 Node.js 24。前端无需安装 npm 包。

```powershell
npm run preview
```

在浏览器打开终端中的 `http://127.0.0.1:4173`。退出预览按 Ctrl+C。双击 HTML 无法正确加载模块和题库，请通过 HTTP 预览。

## 导入原始题库

用户可直接提供 Word、Excel 或文本文件。Word / Excel 应先按原文提取并人工核对段落或单元格边界，再转成下列 JSON；不要自行推断缺失内容。TXT / JSON 可使用脚本检查，支持 UTF-8 与 BOM。TXT 支持每行一题，或 `001、题目` / `1. 题目` 格式的编号题目；编号题目下的非编号行视为该题续行。若原题包含类似编号的子列表，先按 JSON 明确题目边界。

```json
{
  "version": 1,
  "title": "确定关系前的 999 问",
  "questions": [
    { "id": "原始题号", "text": "对应原文" }
  ]
}
```

每题必须有非空字符串 `id` 和 `text`，最后一题的 `id` 固定为 `999`。保留编号（包括前导零）、原文标点和换行。相同数字题号如 `01` / `1` 会报告为重复；忽略空白后相同的内容也会报告。报告仅供确认，不会自动删除、合并、改写。恰好 999 题且所有检查通过才允许写入。

```powershell
# 仅检查，不修改文件
node scripts/import-questions.mjs "题库.txt"
# 核对通过后写入正式题库
node scripts/import-questions.mjs "题库.txt" --write
npm test
npm run check:publish
```

## 抽签与记录

- 从前 998 题中的剩余题目均匀随机抽取，使用 Web Crypto；抽过的题目本轮不重复。第 999 题不会进入随机题池。
- 点击「已聊完」仅记录确认时间，不记录答案。点「先放一放，聊下一题」会将当前题留到待聊列表，并从未抽过的题中抽取下一题。已抽完普通题时，会引导回到待聊列表。
- 可以从待聊列表继续任意一题；当前未聊完的题会自动暂放，历史不会重复计数。暂放不会增加已聊完数量，所有普通题都确认后才可揭开最后一签；最后一签不支持暂放。
- 点击后立即保留并保存本次题目，再播放动画。动画期间阻止连续点击；刷新中断动画仍能恢复这一题。
- 当前题目、历史、待聊列表和已聊完状态仅存本浏览器 `localStorage`，不收集回答。存储受限时改为本次页面的内存记录并提示。记录格式升级至 v3，仍兼容旧 v2 记录，两个版本沿用原有存储键。
- 同源多标签页通过 Web Locks 协调，监听存储变化。旧浏览器若不支持 Web Locks，建议同一时间只在一个标签页抽签。
- 题库内容的 SHA-256 变化时开启新一轮；损坏记录会提示并从零开始。重置只覆盖本应用键，不清除其他网站数据。
- 聊完保留最后一题和历史，通过确认后开启新一轮；重置也会重新锁定第 999 题。支持减少动画、键盘焦点与原生对话框。
- 手机首屏压缩装饰和说明，优先露出抽签操作；抽出或继续题目后滚动到卡片，长题目完整换行。系统选择减少动画时关闭抽签动画和平滑滚动。
- 分享复制当前网页地址，移除无关查询参数和片段，保留当前版本参数；剪贴板不可用时显示可选中的链接。本机预览地址会明确提示不能作为公开分享链接。

## 备份与恢复

在页面底部点击「备份与恢复进度」，导出当前版本的 JSON 文件。文件包含版本、题库指纹、题号、当前卡片及抽签 / 确认 / 暂放时间，不包含回答或题目原文。精简版与完整版需要分别导出。

在另一台设备或浏览器打开网页，选择备份文件，检查显示的版本、已抽数量和备份时间，点击「确认恢复进度」后替换该版本的记录，并切换到导入的版本；另一个版本不受影响。取消导入、格式错误、题库不匹配或超过 1 MB 的文件均不会修改现有进度。导入替换前可先导出一份当前备份。

备份和恢复完全在浏览器内完成，不上传文件。清除浏览器数据或更换网址后，可通过此前保存的备份恢复；存储受限的浏览器仍需妥善保留备份文件。

## 验证与发布

`npm test` 验证 99 / 999 两版完整抽签与确认、最后一题解锁、重复与过期确认、待聊和继续、独立进度与旧版兼容、备份往返与错误文件、记录恢复、题库变化、损坏记录、存储异常、导入检查与静态服务。测试占位只存在于测试进程的内存中，禁止写入正式题库。`npm run check:publish` 会同时检查完整版 999 题和精简版 99 题。

### GitHub Pages

源码仓库：<https://github.com/Dainty-cyber/relationship-999>。

`.github/workflows/pages.yml` 会在 `main` 更新或手动运行时，使用 Node.js 24 执行测试、题库检查及已部署双人服务的匿名验收，通过后仅发布 `dist/` 中的网页。验收用临时房间检查首方答案隐藏、共同揭晓、跨域权限和删除，最后清理测试数据。项目没有 npm 依赖，无需安装依赖或配置个人 Token。

首次发布需要仓库所有者完成一次设置：

1. 打开 <https://github.com/Dainty-cyber/relationship-999/settings/pages>。
2. 在 **Build and deployment → Source** 中选择 **GitHub Actions**。
3. 打开仓库 **Actions → Check and deploy to GitHub Pages**，选择 **Run workflow → main → Run workflow**。如果首次运行在 Pages 未启用时失败，也可以在该次运行中选择 **Re-run all jobs**。
4. 等待运行成功，在 `github-pages` 部署环境或 Pages 设置中获取实际发布网址。自动化流程未成功前，预期网址不代表已上线。

项目网页使用相对资源路径，支持 GitHub Pages 的项目子目录。源码、脚本和测试不会包含在网站发布产物中。不同域名的浏览器记录独立保存，不会自动迁移既有网站的抽签进度。

### 既有 Sites 网站

使用 Sites 技能发布：`.openai/hosting.json` 保留原项目 ID 与个人静态前端声明；`hosting/hosting.json` 是升级后的服务端声明，使用 `DB` 绑定，不声明 `static`。先通过 helper 打开同一个 Sites 远端源码项目，再移入官方 Vinext 模板、`web/` 网页和 `server/` 协议，生成/保留 Drizzle 迁移，构建、推送源码、打包保存版本并部署。保持公开访问，不新建重复站点。生产中也会提供当前网页，GitHub Pages 链接继续有效。

可选浏览器检查：`node scripts/browser-check.mjs --playwright "已有 playwright-core/index.mjs 的绝对路径" --browser "已有 Edge 或 Chromium 的绝对路径"`。脚本仅在本地开启临时服务，用内存中的测试数据验证交互，不会修改正式题库或访问外部网站；退出时关闭浏览器和服务。输出截图位于已忽略的 `outputs/`。

新增交互检查：使用相同参数运行 `scripts/comfort-browser-check.mjs`，验证手机首屏、待聊、旧进度升级、跨浏览器导入、取消导入和最后一题的解锁。可选 `--url "公开网页地址"` 在匿名浏览器中验证已部署的版本；仅操作该测试浏览器内的记录。

双人浏览器验收：使用相同 Playwright / 浏览器参数运行 `scripts/pair-browser-check.mjs`，用两套独立浏览器记录验证盲答、提交响应丢失、刷新与草稿恢复、共同揭晓、双人确认、第三人拒绝和房间删除。可选 `--url "前端地址" --api "同步服务地址"` 验证线上；测试会创建自己的房间并在结束时删除。

页面不请求第三方字体或脚本，所有图形使用本地 SVG 与 CSS。个人模式仍只在浏览器内运行；双人模式会访问上述同步服务。
