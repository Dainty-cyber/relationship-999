# 确定关系前的 999 问 · 遇见彼此

奶油白与浅粉色的手机抽签网页。无框架、无依赖、无账号，正式页面位于 `dist/`。

已按用户提供的 Word 文档导入全部 999 题，保留原始题号与文字。核对结果：题号 1–999 连续，无空题、重复题号或重复内容。

**抽签规则：只从第 1–998 题中不重复抽取；当前题点「已聊完」后才能继续抽签。前 998 题全部确认后，解锁第 999 题。无需填写或上传答案。**

## 本地预览

需要 Node.js 22 或更高版本，无需安装 npm 包。

```powershell
npm run preview
```

在浏览器打开终端中的 `http://127.0.0.1:4173`。退出预览按 Ctrl+C。双击 HTML 无法正确加载模块和题库，请通过 HTTP 预览。

## 导入原始题库

用户可直接提供 Word、Excel 或文本文件。Word / Excel 应先按原文提取并人工核对段落或单元格边界，再转成下列 JSON；不要自行推断缺失内容。TXT / JSON 可使用脚本检查，支持 UTF-8 与 BOM。TXT 支持每行一题，或 `001、题目` / `1. 题目` 格式的编号题目；编号题目下的非编号行视为该题续行。若原题包含类似编号的子列表，先按 JSON 明确题目边界。

```json
{
  "version": 1,
  "title": "确定关系前的 999 问",
  "questions": [
    { "id": "原始题号", "text": "对应原文" }
  ]
}
```

每题必须有非空字符串 `id` 和 `text`，最后一题的 `id` 固定为 `999`。保留编号（包括前导零）、原文标点和换行。相同数字题号如 `01` / `1` 会报告为重复；忽略空白后相同的内容也会报告。报告仅供确认，不会自动删除、合并、改写。恰好 999 题且所有检查通过才允许写入。

```powershell
# 仅检查，不修改文件
node scripts/import-questions.mjs "题库.txt"
# 核对通过后写入正式题库
node scripts/import-questions.mjs "题库.txt" --write
npm test
npm run check:publish
```

## 抽签与记录

- 从前 998 题中的剩余题目均匀随机抽取，使用 Web Crypto；抽过的题目本轮不重复。第 999 题不会进入随机题池。
- 点击「已聊完」仅记录确认时间，不记录答案；确认之前保留当前题，不抽下一题。前 998 题均确认后才可揭开最后一签；最终题确认后完成本轮。
- 点击后立即保留并保存本次题目，再播放动画。动画期间阻止连续点击；刷新中断动画仍能恢复这一题。
- 当前题目、历史和已聊完状态仅存本浏览器 `localStorage`，不收集回答。存储受限时改为本次页面的内存记录并提示。
- 同源多标签页通过 Web Locks 协调，监听存储变化。旧浏览器若不支持 Web Locks，建议同一时间只在一个标签页抽签。
- 题库内容的 SHA-256 变化时开启新一轮；损坏记录会提示并从零开始。重置只覆盖本应用键，不清除其他网站数据。
- 聊完保留最后一题和历史，通过确认后开启新一轮；重置也会重新锁定第 999 题。支持减少动画、键盘焦点与原生对话框。
- 分享复制当前网页地址，移除查询参数和片段；剪贴板不可用时显示可选中的链接。本机预览地址会明确提示不能作为公开分享链接。

## 验证与发布

`npm test` 验证完整 999 次抽签与确认、最后一题解锁、重复与过期确认、记录恢复、题库变化、损坏记录、存储异常、导入检查与静态服务。测试占位只存在于测试进程的内存中，禁止写入正式题库。`npm run check:publish` 是正式题库的发布门槛。

### GitHub Pages

源码仓库：<https://github.com/Dainty-cyber/relationship-999>。

`.github/workflows/pages.yml` 会在 `main` 更新或手动运行时，使用 Node.js 24 执行测试和题库检查，通过后仅发布 `dist/` 中的网页。项目没有 npm 依赖，无需安装依赖或配置个人 Token。

首次发布需要仓库所有者完成一次设置：

1. 打开 <https://github.com/Dainty-cyber/relationship-999/settings/pages>。
2. 在 **Build and deployment → Source** 中选择 **GitHub Actions**。
3. 打开仓库 **Actions → Check and deploy to GitHub Pages**，选择 **Run workflow → main → Run workflow**。如果首次运行在 Pages 未启用时失败，也可以在该次运行中选择 **Re-run all jobs**。
4. 等待运行成功，在 `github-pages` 部署环境或 Pages 设置中获取实际发布网址。自动化流程未成功前，预期网址不代表已上线。

项目网页使用相对资源路径，支持 GitHub Pages 的项目子目录。源码、脚本和测试不会包含在网站发布产物中。不同域名的浏览器记录独立保存，不会自动迁移既有网站的抽签进度。

### 既有 Sites 网站

使用 Sites 技能发布：当前目录是站点源目录，`.openai/hosting.json` 已记录静态目录 `dist` 和云端站点 ID，后续更新复用同一 ID。打包前运行题库门槛，核对通过后同步源代码、保存版本、将访问范围设为公开并部署，验证返回的生产网址。不得将本地预览地址作为公开网址交付。

可选浏览器检查：`node scripts/browser-check.mjs --playwright "已有 playwright-core/index.mjs 的绝对路径" --browser "已有 Edge 或 Chromium 的绝对路径"`。脚本仅在本地开启临时服务，用内存中的测试数据验证交互，不会修改正式题库或访问外部网站；退出时关闭浏览器和服务。输出截图位于已忽略的 `outputs/`。

网页无业务后端、无第三方脚本或字体请求。所有界面图形使用本地 SVG 与 CSS 绘制。
